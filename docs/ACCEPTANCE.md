# Beyond: Craftlines 验收文档

本文用于验收合成链供给器的配方类型确认 GUI。案例使用 Create 工作盆，因为同一个
`create:basin` 催化剂通常会被 JEI 同时登记到以下配方类型：

- `create:mixing`：搅拌；
- `create:packing`：压块，对应服务端 `create:compacting` 配方族。

界面显示文本会随机器模组/JEI 语言包变化，验收时以 JEI 当前登记结果为准。三个支持版本
都必须执行本验收；若对应版本提供 Create 工作盆，则预期至少出现“搅拌”和“压块”两项，
否则应选择一个在 JEI 中登记到至少两个配方类型的机器作为等价案例。

## 1. 验收环境

| Minecraft | 加载器 | Java | Beyond Dimensions / JEI |
| --- | --- | ---: | --- |
| 1.20.1 | Forge 47 | 17 | 使用 `versions/1.20.1/gradle.properties` 声明的版本 |
| 1.21.1 | NeoForge 21.1 | 21 | 使用根目录 `gradle.properties` 声明的版本 |
| 26.1.2 | NeoForge 26.1.2 | 25 | 使用 `versions/26.1.2/gradle.properties` 声明的版本 |

每行都使用当前待验收的 Beyond: Craftlines 构建。机器模组应选择该 Minecraft 版本可用且
能让同一催化剂对应至少两个 JEI 配方类型的版本。

建议新建测试世界并开启作弊。验收玩家需要先连接一个 Beyond Dimensions 网络，并拥有该网络的管理员权限。

准备以下物品：

- 合成链供给器；
- 网络连接器；
- Create 工作盆；
- Jade（用于检查最终启用类型，可选但推荐）。

## 2. 基础布置

1. 确认当前玩家已连接到一个自己可管理的 Beyond Dimensions 网络。
2. 放置合成链供给器，确认它已绑定到当前网络。
3. 在附近放置一个 Create 工作盆。
4. 确认 JEI 中工作盆被登记为搅拌和压块配方的催化剂。

预期结果：供给器和工作盆均保持加载，供给器可正常识别当前网络；此时尚未扫描工作盆。

## 3. GUI 默认可打开，未扫描时提供手动兜底

1. 不使用网络连接器，普通右击合成链供给器。
2. 观察供给器 GUI。

预期结果：

- GUI 正常打开，不要求先完成工具绑定；
- 界面显示配方类型搜索框；聚焦或输入时展开下拉列表，最多显示五行并支持滚轮滚动；
- 搜索同时匹配 JEI 本地化分类名和 `namespace:path` UID，悬停项使用天穹物流标签过滤列表风格的青色高亮；
- 下拉框严格单选，只能选择一个父配方类型，不能累计多个父类型；
- 选择后服务端验证该类型能解析到当前已加载配方族，验证成功后重新打开配置界面；
- 重新打开的界面固定显示所选父类型，并展示该类型可用的子标签/材料组供玩家继续配置。
- 供给器侧面在没有目标方块图标时显示该父类型的 JEI 本地化名称；标题不可用时显示 UID。

## 4. 使用工作盆生成候选选项

1. 关闭供给器 GUI。
2. 手持网络连接器，潜行右击合成链供给器。
3. 确认出现“已选择此合成链供给器”的提示。
4. 使用同一个网络连接器普通右击 Create 工作盆。
5. 确认出现“已将识别到的配方类型加入供给器候选项”的提示。
6. 普通右击供给器，重新打开 GUI。

预期结果：

- GUI 中出现工作盆经 JEI 识别得到的候选类型；
- Create 6.0.9 标准环境中至少包含“搅拌”和“压块”，对应 UID 分别为
  `create:mixing` 和 `create:packing`；后者必须解析为服务端 `create:compacting` 配方族；
- 新出现的候选项默认未启用，扫描动作本身不会自动让供给器承接这些配方；
- 已存在扫描候选时不显示手动下拉，仍只能操作扫描候选。

如果没有出现扫描选项，先在 JEI 中确认工作盆确实是对应 category 的正式催化剂，再检查 JEI
运行时索引是否已经初始化；候选为空时可使用单选手动兜底，但仍必须通过服务端配方族校验。

### 4.1 单候选自动启用

1. 使用一个候选为空、尚未配置的供给器。
2. 选择该供给器后，扫描一个只对应单个 JEI 配方类型的机器，例如仅识别出粉碎配方的 Mekanism 粉碎机。
3. 不打开供给器 GUI，直接查看绑定反馈与 Jade。
4. 再打开供给器 GUI 核对选项。

预期结果：

- 绑定反馈明确提示唯一候选已自动选中并启用；
- 无需进入 GUI 点击一次，该配方族已经能被规划器使用；
- Jade 立即显示这一条已启用类型；
- GUI 打开后该唯一候选已经勾选；
- 若供给器后来累计为多个候选，不自动替玩家启用新增候选。

### 4.2 拒绝非 JEI 催化剂的储物设备

1. 放置一个具有物品或其他已注册储物能力、但未被 JEI 登记为任何配方分类催化剂的方块。
2. 不选择供给器，手持网络连接器普通右击该方块，尝试直接绑定。
3. 选择供给器后再次右击该方块，尝试把它加入供给器候选。

预期结果：

- 两次操作都明确提示“设备 `<namespace:block_id>` 未在 JEI 中注册为任何配方催化剂”，其中 ID 必须是当前目标方块的实际注册 ID，且提示中不出现空的分类列表或多余占位标点；
- 该方块不会因为拥有储物能力而创建直接机器绑定，也不会加入供给器候选；
- JEI 正式登记为催化剂且具备可自动化能力的设备仍可正常绑定。

## 5. 手动确认单个配方类型

1. 在供给器 GUI 中只勾选“搅拌”。
2. 保持“压块”未勾选。
3. 关闭并再次打开供给器 GUI。
4. 使用 Jade 查看供给器提示。

预期结果：

- 再次打开 GUI 后，“搅拌”保持勾选，“压块”保持未勾选；
- Jade 只显示已启用的“搅拌”，不显示仅作为候选存在的“压块”；
- Craftlines 将该供给器视为 `create:mixing` 的可用供给端点；
- Craftlines 不会将该供给器视为 JEI `create:packing`（服务端 `create:compacting`）的可用供给端点。

## 6. 手动确认多个配方类型

1. 再次打开供给器 GUI。
2. 同时勾选“搅拌”和“压块”。
3. 关闭并重新打开 GUI。
4. 使用 Jade 查看供给器提示。

预期结果：

- 两个选项均保持勾选；
- Jade 同时显示“搅拌”和“压块”；
- 供给器可同时作为 JEI `create:mixing` 和 `create:packing` 的供给端点，后者承接
  `create:compacting` 配方族。

## 6.1 多材料组筛选

使用会公开多个逻辑输入部分的配方类型，例如 `goety:ritual` 的普通材料与激活物品：

1. 扫描对应机器并在供给器 GUI 中勾选该配方类型。
2. 确认主按钮下方出现一组宽度更窄的材料组按钮，初始均未勾选。
3. 保持全部材料组未勾选并提交一次订单。
4. 只勾选“激活物品”，再次提交订单。
5. 在另一个供给器上只勾选“材料”，并让两个供给器共同完成一次订单。
6. 取消“激活物品”，使其再次回到全部未勾选。

预期结果：

- 二级按钮支持多选，关闭并重新打开 GUI 后保持选择；
- 全部未选表示接受所有材料组，不会导致该供给器拒绝全部材料；
- 选择任意组后切换为白名单，只向该供给器投送被选组；
- 不同材料组可同时投送到不同供给器，产物返回前所有参与供给器保持占用；
- 取消最后一个二级选项后恢复接受全部；
- 只有一个逻辑材料组的配方类型不显示二级按钮，行为与旧版本一致。

## 6.2 Malum 精魂与网络入口偏好

1. 为同一产物保存一个非首位配方偏好。
2. 确认 Minecraft「按键控制」的 Beyond: Craftlines 分类中存在“下单悬浮资源”（默认中键），在 BD 网络物品槽悬浮该产物并按此键，等待订单树完成规划。
3. 分别在 JEI 配方槽、物品列表和书签列表悬浮该产物并按同一按键；将其临时重绑为键盘键后重复验证。
4. 从 JEI 的另一条具体配方点击 Craftlines 按钮打开同一产物。
5. 打开 Malum `spirit_infusion` 配方，例如神圣金锭。
6. 分别打开已有偏好的配方候选页和 Tag/OR 原料候选页，点击右上角“遗忘偏好”。

预期结果：

- 网络按键入口使用已保存偏好，没有有效偏好时才使用首个可用配方；
- 三个 JEI 按键入口均打开同一产物的订单树，使用与网络按键入口一致的配方偏好；
- JEI 入口的自动规划仍保持被点击的具体配方，不被根节点偏好自动替换；玩家在本次合成树中显式手动切换根配方后，按手动选择重新规划；
- 没有已保存偏好时候选页不显示“遗忘偏好”；存在偏好时按钮出现，点击后删除对应客户端持久偏好和本次覆盖、关闭候选页并恢复自动选择；
- Ctrl 右击和 Ctrl+Shift 右击不再承担清除配方或原料偏好的语义；
- Malum 1.20.1 的 `SpiritWithCount#getStacks()` 和 1.21.1 的 record `SpiritIngredient#getItems()`
  均展开为带正确数量的精魂碎片输入；
- 缺料汇总列出真实缺失的金锭、石英或精魂碎片，不把目标产物本身误报为原料。

## 6.3 递归 JEI 候选上传

1. 选择至少三层、每层存在多个 JEI 配方候选的产物。
2. 在树中分别保留自动候选和手动替换一个递归子配方。
3. 提交预览，确认只上传实际选中的虚拟配方描述，而不是整个 JEI 目录。
4. 修改一个上传描述的 family、输入数量或确定性 ID，确认服务端拒绝固定链。

预期结果：

- 每个递归节点的输入、数量与子标签均来自对应 JEI 布局；
- 服务端不查询 RecipeManager 或 recipe IO profile 来补全递归节点；
- 上传按 8 条描述分页并受 64 页、32 槽、每槽 64 候选限制；
- 自动和手动候选均能通过固定链线性复算，篡改描述不能进入订单。

## 6.4 JEI 类型一次性预热

将客户端 `planning.preloadAllRecipeTypes` 设为 `false`，验证按需模式。

1. 进入世界后等待当前有效网络已启用配方类型的后台预热完成，首次打开其中一种类型的配方树。
2. 关闭后再次打开相同目标和同类型的另一个目标。
3. 再启用一种此前未使用的机器类型并首次打开其配方树，随后重新打开第一种类型。

预期结果：

- 同一 JEI runtime 生命周期内，每个 category 最多完整物化一次；
- 第二次打开相同类型不再显示“正在索引配方”或重新创建该类型的 drawable；
- 新类型只追加自身的虚拟描述，不清空已完成的原生配方索引和规划目录缓存；
- 配方数据包重载、JEI runtime 重建或退出世界后才允许重新预热。

## 6.5 跨登录规划目录缓存与手动重载

以下步骤分别适用于 1.20.1 Forge、1.21.1 NeoForge 与 26.1.2 NeoForge：

1. 完成当前网络的配方加载，确认日志出现 `client planning catalog ready` 后，继续等待 `client planning cache saved`，后者才表示磁盘文件已安装成功。核对日志中的路径、配方数、条目数与文件大小；不得仅凭 `catalog ready` 判定落盘。
2. 退出并重进同一世界／服务器，再重启游戏重复一次。holder ID 集合未变时应出现 `client planning cache restored`，不因登录或 JEI 初始化而强制重新捕获规划目录；读取期间显示“正在读取配方缓存”。JEI 描述命中的分类直接恢复，只有未命中的分类重新创建布局。
3. 切换另一存档或服务器，确认缓存范围独立；切回原范围仍能复用其文件。
4. 普通玩家执行 `/craftlines reload`，确认无需 OP、不会发送服务器全局重载，当前范围缓存清除并重新捕获；完成后再次重进应读取新缓存。
5. 修改 ID 不变的配方／标签／IO profile 后执行该命令，确认规划使用更新内容。增加或删除少量配方 ID 时，应按 ID 增量更新，日志中的 reused 应保留未变配方，只补捕获新增 ID 并移除删除 ID；损坏缓存文件时才回退重新捕获。
6. 在保存进行中手动重载，确认旧保存不会覆盖重载后结果；退出期间旧 generation 不得安装结果。

## 6.6 默认全类型预热

分别在 1.20.1 Forge、1.21.1 NeoForge 和 26.1.2 NeoForge 验证：

1. 使用默认客户端配置 `planning.preloadAllRecipeTypes=true`，进入尚未绑定机器、没有可用网络的新世界，确认后台开始全部 JEI 分类及受支持配方的预算预热。
2. 等待目录完成，再绑定熔炉并启用烧炼，随后启用其它机器类型、取消类型或切换网络；不得清空已完成全量目录或重新捕获已有配方。
3. 网络 A 只启用烧炼，网络 B 只启用混合，两者共享全量缓存，但候选与递归规划均只能使用各自启用的类型；不可因缓存中存在某配方而越过网络执行限制。
4. 在超过 20 万条配方的全量目录（如 ATM10）中，等待 `client planning cache saved` 后退出／重启并重进同一世界，确认出现 `client planning cache restored`，不再进入 `recipe_capture`；执行 `/craftlines reload` 后重新全量捕获。未命中或保存失败时必须有具体原因和缓存路径。不得因缓存配方数、累计条目／字符串／NBT 或文件大小超过旧上限而拒绝保存／读取。
5. 将配置设为 `false` 后重进，确认恢复按网络类型预热；切回 `true` 后重新得到完整目录。
6. 整合包包含超过 16,384 条 JEI 虚拟描述时，确认最先完成的分类仍可查询，下单入口不会因为 LRU 淘汰而丢失。

## 6.7 慢配方日志

三个支持版本均使用同一阈值与限流规则：

1. 在测试环境令某个 JEI 布局创建、配方输入／输出 accessor 或单候选处理调用耗时超过 20ms，完成预热后在 `logs/latest.log` 或 `logs/debug.log` 搜索 `slow recipe index`。
2. 确认明细能区分 `jei_layout`、`jei_capture`、`jei_register`、`recipe_outputs`、`recipe_inputs`、`recipe_samples`、`recipe_candidate`、`recipe_finalize`；带稳定配方 ID、分类／类型、实现类、单次耗时和线程名。没有 JEI 稳定 ID 时显示分类内序号，未知数量为 `-1`。
3. 检查 `recipe_snapshot` 的后台线程与渲染线程日志可以区分；`index_frame`、`recipe_step`、`catalog_index` 和 `lookup_index` 是聚合处理时间，不误解为单配方或整帧耗时。
4. 重复处理同一慢配方同一阶段，确认明细不重复，汇总中的 `calls`／`suppressed` 继续增长；超过 128 个不同明细后只提示一次限额，同时仍汇总最慢配方。
5. `/craftlines reload` 后重复操作，确认允许重新输出同配方明细；异常抛出路径仍有计时，但原有异常处理行为保留。正常快速配方不应新增逐条日志。

## 6.8 ATM10 8.1 新版 JEI 与工作站输入缓存

适用于三个支持版本的通用桥接／缓存行为；ATM10 8.1 运行复测使用 Minecraft 1.21.1 NeoForge：

1. 使用返回直接布局的旧版 JEI，以及返回 `Optional<RecipeLayout>` 的新版 JEI，确认显式 focus link 均能被捕获；Optional 为空不创建伪布局记录，真正缺失桥接时仍拒绝描述。
2. ATM10 8.1 / JEI 19.57.0.446 中为供给器启用符文之星祭坛类型，完成重载后打开 ATM 之星配方树。确认原来 `JEI layout relation bridge is unavailable` 的拒绝消失，祭坛候选进入树；材料仍保留数量、组件和可复用语义。
3. 搜索 `client target candidates`：`indexed` 为当前目标的全局候选数，`available` 为通过菜单网络过滤的候选数，`familyIds` 和 `candidateRecipes` 列出有界诊断信息。零全局候选与有候选但网络过滤后的零候选可以区分；Unsupported 日志包含配方身份、实际布局实现类和拒绝原因。
4. 预热 Silent Gear 锻造类型，确认资源捕获后样本／余料读取复用同一份工作站输入，不再次整表枚举物品；非工作台配方不构造工作台基线样本。使用 `/craftlines reload` 后解析缓存必须更新。

上游依据：[JEI 1.21.1 的布局构造返回值](https://github.com/mezz/JustEnoughItems/blob/1.21.1/Library/src/main/java/mezz/jei/library/gui/recipes/layout/builder/RecipeLayoutBuilder.java)、[ATM10 官方星祭坛配方脚本](https://github.com/AllTheMods/ATM-10/blob/main/kubejs/server_scripts/modpack/runic_multis/recipes/star_altar.js)。

## 6.9 原生 EMI 查看器的星祭坛兜底

通用声明／权限逻辑覆盖三个支持版本；下列 ATM10 自定义家族仅在真实注册该家族的整合包中生效，不假设其它版本安装了 MI 或存在同名机器。

1. 在 ATM10 8.1 的 JEI＋EMI 环境启用 `modern_industrialization:star_altar`，等待目录完成。确认 `client native fallback indexed` 包含真实 `modern_industrialization:kjs/...` 配方 ID，`client target candidates` 的 `available` 包含祭坛候选而非只有星块拆解。
2. 展开 ATM 之星，核对 28、15、2 等材料数量及附魔／命名组件；缺料时仍显示祭坛分支。服务端固定链必须重新读取同一个原生配方 ID，网络供给器仍负责真实投料和产物回收。
3. 取消祭坛类型或切换到没有该端点的网络，确认原生候选被过滤且服务端不能绕过绑定检查。

5. 在两个中间步骤都未完成时确认父步骤没有提前投料；两者完成后父步骤才变为可执行。
6. 加工期间保存并重启世界，确认多个在途步骤及各自进度能够恢复，且同一机器仍不会收到重复分派。

## 14. 已绑定机器左击配置与防破坏

1. 分别在生存和创造模式中，主手持网络连接器左击已绑定机器。
2. 改为副手持连接器后重复测试。
3. 勾选多个候选配方类型，关闭界面并重新打开。
4. 对含 `activation_item` 与 `offerings` 的仪式配方，将祭坛仅设为 `activation_item`，将多个单槽基座仅设为 `offerings`，以阻挡模式下单。
5. 再取消基座直绑，改用仅接受 `offerings` 的供给器和外部管道给基座投料，以阻挡模式重复下单。
6. 左击未绑定方块、已失效绑定和无管理权限网络中的机器。
7. 在专用服务器上重复创造模式测试，并尝试持续按住攻击键。

预期结果：

- 已绑定机器打开配方类型配置界面，不显示“全部送回网络”按钮；
- 配置由服务端自动保存，重新打开后保持一致；
- 直接绑定方案按材料组将起手物送入祭坛，并把供品分布到多台单槽基座；一个阻挡批次只投送一次配方所需材料，仪式产物从任一参与的直接机器回收后完成该批次；
- 混合方案将起手物直接送入祭坛、把供品送入供给器供管道分发，并继续从参与的祭坛回收产物；供给器不会抢占未分配给它的材料组；
- 创造模式下机器不会被破坏，也不会出现客户端闪碎；
- 主手和副手持连接器都不会绕过保护；
- 未绑定、失效、超距或无权限目标不会打开界面；
- 不持连接器时仍保持原版方块破坏行为。

## 15. 端点优先级

1. 准备两个接受同一配方类型、同一材料组的供给器或已绑定机器。
2. 分别打开两种配置 GUI，确认倒数第二行显示 `-10`、`-1`、当前值、`+1`、`+10`。
3. 把一个端点设为 `10`、另一个保持 `0`，关闭并重新打开界面核对持久化。
4. 下单并确认数值 `10` 的端点先被选择；交换优先级后再次验证。
5. 将高数值端点改为通配材料组、低数值端点显式选择目标材料组，确认显式组仍优先。
6. 连续点击优先级按钮，确认不会触发配方类型的全量重扫或明显卡顿。

## 16. 跨订单配方类型并发

1. 在同一 BD 网络提交两个仅使用不同非普通合成配方类型的订单，例如一个只含 `smelting`、另一个只含 `create:mixing`。
2. 保持前一个订单加工中，确认后一个订单也能开始执行。
3. 再提交两个都包含 `smelting` 的订单，确认后一订单显示“正在等待更早的网络订单”，直到前一订单结束。
4. 提交两个都包含普通 `crafting`、但其他配方类型互不相同的订单，确认 `crafting` 重合不阻止并发。
5. 将 `crafting.maxConcurrentOrdersPerNetwork` 设为 `2`，提交三个配方类型互不相交的订单，确认同一时刻最多执行两个；设为 `1` 后确认恢复严格 FIFO 串行。
6. 在两个不同 BD 网络各提交一个使用相同配方类型的订单，确认两个网络互不阻塞。

## 18. 验收结论

以下条件全部满足时，本功能通过验收：

- 供给器 GUI 无需预先扫描即可打开；
- 未扫描且未配置时提供可搜索、可滚动的 JEI 配方类型单选下拉；
- Create 工作盆扫描后能展示 JEI 返回的多种配方类型；
- 扫描不会自动启用类型，必须由玩家勾选并保存；
- 可以独立启用、取消或同时启用“搅拌”和“压块”；
- 手动下拉只能选一个父类型，服务端验证后重开界面并提供该父类型的子标签；
- 已有扫描候选或现有父类型时不开放候选集外提交；
- 权限、持久化、Jade 展示和库存提取行为符合上述预期。
- 订单状态页默认只展开第一条、能展开全部未完成步骤、正确合并同类资源，并可用左键折叠；已完成和已取消订单均在 5 分钟后消失。
- 同订单内无依赖且使用不同机器的步骤可以并行，同一机器仍严格互斥，父步骤不会越过未完成依赖。
- 同网络订单仅在非普通合成配方类型无交集且未达到配置上限时并行；`crafting` 不参与冲突，不同网络互不阻塞。
- 手持连接器左击已绑定机器可以配置候选配方类型，机器模式没有回库按钮，创造模式不会破坏机器。
- 两种配置 GUI 都能持久化优先级；同组匹配等级内数值更高者优先，显式材料组仍先于通配组。

## 0.5.3 供给器均分模式

分别在 Minecraft 1.20.1 / Forge、1.21.1 / NeoForge、26.1.2 / NeoForge 执行：

1. 按 A、B、C 顺序绑定三个空供应目标，另加一个抽取连接；按钮循环到“均分”。
2. 通过订单暂存 8 个铁锭和 8 个铜锭；两种资源均应得到 A=3、B=3、C=2，抽取连接不参与。
3. 下一批重复，仍优先 A；4 个资源为 2/1/1，6 个资源为 2/2/2。
4. 将 A 的可插入容量限制为 1，发送 8 个资源，应为 1/4/3；A 拒收时为 0/4/4。
5. 总容量不足时确认剩余资源仍在供给器；腾出容量后自动继续发送，无丢失或复制。
6. 保存重进确认均分模式保留；旧存档三个模式及轮询重置配置行为不变。

这些是游戏内人工验收步骤；自动构建和算法测试不替代实际模组能力交互验收。

## 转交存档与非主网络下单

分别在 Minecraft 1.20.1 / Forge、1.21.1 / NeoForge、26.1.2 / NeoForge 执行，使用 BD 0.7.30 或更新版本：

1. 玩家 A 在网络 N 中配置供给器、供应面和抽取面，放入足够原料并保存退出。将完整存档交给玩家 B，以不同 UUID 加载。
2. 给 B 加入 N 并授予管理员权限，保留 B 的另一个主网络 P；P 不放对应原料，也不配置对应机器。确认 B 正在打开的 BD 界面是 N。
3. 从 N 的界面下单，选择产物回网络，确认预览读取 N 的库存和绑定；原料从 N 投送到原有供给器，最终产物回到 N，P 不发生库存变化。A 无需在线。
4. 从 N 的侧边栏打开合成状态和监控面板状态，确认显示 N 的订单和面板，而非 P 的内容。取消未完成订单，确认预留材料返还 N。
5. 关闭 BD 界面，从 JEI 直接打开合成链，确认仍按刚使用的 N 规划。打开 P 的 BD 终端后关闭，再从 JEI 进入，确认此时改用 P。
6. 保存重进，重复第 3 步，确认旧绑定和无线连接保留。移除 B 的 N 成员与管理员权限后，确认无法继续通过合成链界面向 N 下单。

仅成为网络管理员不等于切换主网络。从 BD 界面进入时以该界面网络为准，从 JEI 直接进入时优先使用上次实际打开且仍可访问的网络，无有效记忆时才以玩家主网络为准。此场景尚需游戏内人工验收；构建通过不代表已在玩家存档复现。

## 0.6.0 烧炼候选、循环回退与索引稳定性

通用配方规划规则覆盖 Minecraft 1.20.1 / Forge、1.21.1 / NeoForge、26.1.2 / NeoForge。EMI 入口在 1.20.1 和 1.21.1 核验；26.1.2 的 EMI 接口仍为空实现，使用 JEI 核验同一套原生配方与循环回退规则。

- 原生 `smelting`、`blasting`、`smoking` 保留服务端配方 ID，进入客户端候选索引，但仅对已启用对应家族的网络可见。
- 快速规划在时间与节点预算内跳过循环或缺料候选，找到可用分支后停止额外优化；自动生成的初始树不充当玩家手动锁定。
- 未完成的候选搜索显示预算耗尽，不宣称所有候选都是循环；存在非循环缺料方案时优先展示该方案。
- EMI 新管理器的发布不再无条件清空 JEI 布局与规划目录；仅在 JEI 分类快照变化时重建。打开订单树时，后台网络可用性轮询不覆盖该菜单的配方家族范围。

人工复测步骤（包括反馈使用的 ATM10 8.1）：

1. 绑定 Iron Furnaces 钻石熔炉，在机器设置启用烧炼，网络放入粗铁，机器提供燃料。点击 EMI 中粗铁烧炼为铁锭配方的合成链按钮，确认根节点保留烧炼方式，并能投料、取得铁锭。
2. 同时保留铁锭／铁粒／铁块的压缩和分解配方。自动规划应绕过循环；缺少粗铁时显示缺少原料。手动锁定循环配方后仍应拒绝该循环。
3. 配方输入使用包含循环项和可行项的标签，确认自动选择可行项。测试烘烤、烟熏，以及未启用对应类型时不可选择相关配方。
4. 完成一次加载后保持订单树打开，反复悬浮配方类型、等待至少 30 秒，确认元数据读取和后台网络轮询不会再次触发已完成分类的加载。真正的数据包／配方重载仍须更新索引。
5. 按上一节配置主网络 P 和菜单网络 N，确认打开 N 的树期间不会被 P 的后台轮询替换目录。

上游核对：Iron Furnaces NeoForge [4.3.2 的 JEI 注册](https://github.com/Qelifern/IronFurnacesNeoForge/blob/4.3.2/src/main/java/ironfurnaces/jei/IronFurnacesJEIPlugin.java)将钻石熔炉注册到标准 `RecipeTypes.SMELTING` 和 `RecipeTypes.FUELING`。此修复补齐通用原生烧炼索引，无需添加猜测的模组分类映射。

上述模组交互步骤需要游戏内人工验收；算法回归与构建检查不代表已在 ATM10 8.1 玩家环境完成复现。


## 上次使用网络记忆

三个版本均执行：Minecraft 1.20.1 / Forge、1.21.1 / NeoForge、26.1.2 / NeoForge（26.1.2 使用 JEI；另两个版本分别检查 JEI 与 EMI）。

1. 首次使用且没有记忆时，在背包中从 JEI 中键下单，应使用玩家主网络 P。
2. 玩家有共享网络 N 的访问权限，打开 N 的 BD 终端后关闭。在背包中从 JEI 中键下单或点击配方下单按钮，应使用 N 的库存与机器绑定。无需把 N 设为主网络。
3. 打开其他箱子、背包，等待后台轮询，随后下单仍使用 N；在 N 的订单树中等待时索引范围保持 N。
4. 打开 P 的 BD 终端，再次直接下单应改用 P。当前打开的网络菜单始终优先于旧记忆。
5. 保存重进，确认记忆保留；另一名玩家的记忆互不影响，换到独立存档不继承该记录。
6. 删除 N 或移除该玩家对 N 的全部访问权限后，从背包直接下单，应清除无效记忆并回退可访问的主网络；主网络也不可访问时显示网络不可用。已打开的显式网络菜单失去权限后，不能静默向另一个网络下单。

网络选择优先级有三版本共享单元测试，NBT 保存／加载、旧存档、玩家隔离及清理记录有 26.1.2 运行环境测试。菜单事件的真实模组交互仍需游戏内人工验收。

## 6.13 JEI 描述持久化与规划目录增量恢复

适用于 1.20.1 Forge、1.21.1 NeoForge、26.1.2 NeoForge：

1. 首次加载后等待 `client JEI cache save result=INSTALLED` 和 `client planning cache saved`，再退出世界／重启游戏。重进应记录 `client JEI cache restored` 与 `client planning cache restored`；命中分类不得逐条调用 `createRecipeLayoutDrawable`。检查配方树、供给器输入组、工具消耗、概率／保证副产物及下单描述仍正确。
2. 只修改一个分类的原始配方 ID：该分类重新物化，其他分类恢复。规划目录中同 ID 记录必须复用，新增 ID 才补捕获，删除 ID 不得再成为候选；删除模组导致旧资源类型未注册时，不得阻止其余分类／配方复用。
3. 同一 ID 包含多个产出方向时，增量合并保留全部方向；只删除 ID 时不得调用任何配方捕获 accessor。
4. 观察进度文案：读取 JEI 缓存、检查配方标识、读取规划缓存、补充配方索引、建立查询索引分别显示，补充索引进度只计算待补配方。全量模式不得显示“已启用类型”。
5. 在缓存读取／后台查询索引准备期间退出或切换世界，旧任务不得填入新世界注册表或发布查询索引。执行 `/craftlines reload` 同时清除 JEI 描述和规划缓存，旧保存不得把已删除文件重新装回。
6. 损坏 JEI 缓存应明确报错并回退；26.1.2 缓存完全命中时仍能解析原生工作台、烧炼与显式 native fallback 配方，不能因为跳过布局而丢失 RecipeCatalog。
