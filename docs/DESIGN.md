# Beyond: Craftlines 统一设计文档

本文档描述当前 `beyond_craftlines` 源码已经实现的功能和约束。它是本项目唯一的设计文档；若文档与代码不一致，以当前源码、注册表和模组元数据为准。

## 1. 项目定位

Beyond: Craftlines 是同时面向 Minecraft 1.20.1 Forge、1.21.1 NeoForge 和 26.1.2 NeoForge 的 Beyond Dimensions（下称 BD）下单附属模组。除非明确标记为版本专用，本文所有功能与约束均适用于三个版本。

它负责把服务端已加载的配方组织成可执行订单，并使用 BD 网络库存完成递归备料、普通合成、原生网络炉加工或第三方机器加工。

项目基础信息：

| 项目 | 当前值 |
| --- | --- |
| 模组 ID | `beyond_craftlines` |
| 支持矩阵 | `1.20.1` / Forge 47 / Java 17；`1.21.1` / NeoForge 21.1 / Java 21；`26.1.2` / NeoForge 26.1.2 / Java 25 |
| 必需依赖 | 各版本对应的 Beyond Dimensions 与 JEI 构建，具体版本见各自 `gradle.properties` |
| 可选显示联动 | Jade |
| 当前版本 | `0.3.0` |

本模组不再包含构象捕获、测试维、沙盒试产、试产报告、稳态产线、图纸复制或相关命令。这些内容不属于当前 JAR。

## 2. 玩家可见内容

当前只注册以下内容：

| 类型 | 注册名 | 作用 |
| --- | --- | --- |
| 物品 | `beyond_craftlines:network_linker` | 将原版或第三方机器及配方类型关联到当前 BD 网络；潜行使用可解绑 |
| 方块/方块物品 | `beyond_craftlines:craftline_provisioner` | BD 联网的订单输入交付端点，只接受订单内部写入 |
| 菜单 | `beyond_craftlines:craftline_order` | 查看 JEI 指定产物的递归树、设置数量和阻挡模式、下单及取消订单 |
| 创造模式页 | `beyond_craftlines:main` | 收纳网络连接器和合成链供给器 |

网络连接器不可堆叠。供给器继承 BD 的联网方块语义，并持久化自己的动态资源库存。

## 3. 总体数据流

```text
任意界面中的 JEI 配方（玩家须有有效 BD 网络）
        │ Craftlines 按钮
        ▼
服务端打开订单菜单并固定 networkId
        │
        ├─ 服务端：签发库存 revision + 配方 epoch 的分页快照
        ├─ 客户端后台：候选搜索、库存抵扣、缺料汇总、配方树
        ├─ 客户端：分页上传完整固定选择
        ▼
短期缓存已完整上传的固定选择
        ▼
点击下单后，服务端按最新库存线性复算
        ├─ 缺料 ──────────► 报错，不创建订单
        ▼
持久化 RecipeOrderJob
        ▼
每 tick 按网络 FIFO 尝试取得库存事务权；非普通合成配方族无交集的订单可并行，并在各订单内推进就绪步骤
        ├─ crafting ───────► 服务端模拟原配方
        ├─ smelting 系列 ──► BD 网络熔炉/高炉/烟熏炉
        ├─ 第三方配方族 ───► 直接绑定机器的物品能力
        └─ 供给器配方族 ───► 交付订单输入后推进步骤
```

服务端是库存变化、计划有效性、订单状态和绑定权限的唯一权威。客户端基于服务端签发的只读库存快照搜索建议配方树，并负责页面中的库存抵扣、取料和缺料预览；点击下单后，服务端才按当前配方注册表和最新网络库存完整复算固定选择，缺少任一材料时直接报错且不创建订单。

第三方机器配方可能把原版 `Recipe#getIngredients()` 或 `getResultItem()` 保持为空。此时规划器从配方公开的通用输入、输出 accessor 或公共字段读取结构化数据；能力式 I/O 容器中的 `content` / `getContent` 包装无论实现为 record 还是普通 class 都只解包实际资源，不把 chance 等元数据当材料；自定义物品 ingredient 以其实际候选为准，不依赖原版内部空值标记。输入和输出中的 `Ingredient` 均通过编译期映射后的 Minecraft API 展开，不使用会在生产混淆环境失效的方法名反射。input representations 通过 BD `IStackKey` 注册表转换为统一资源。物品、流体以及已加载 Mekanism 联动所注册的化学品等资源共同参与客户端树、库存抵扣、缺料与网络提取汇总、计划签名、服务端校验、订单预留和机器投送。依赖运行时输入才能确定产物的动态配方不作为固定产物机器配方索引。

## 4. JEI 入口与订单界面

### 4.1 JEI 入口

JEI 插件为存在物品产出且具有注册 ID 的配方增加网络连接器图标按钮。拥有有效 BD 主网络的玩家默认在任意界面打开 JEI 时均可看到并使用；没有网络时不显示。客户端配置可将其进一步限制为仅在 BD 网络菜单中可用。点击后会同时传递产物 ID 和当前 JEI 配方 ID；订单树的后台自动规划保持该配方为根配方，但玩家对根节点的显式手动 resolution 优先，并按新根配方重新规划。从 BD 网络物品槽按统一的“下单悬浮资源”键（默认中键）进入时不携带固定配方：服务端只提供一个经过能力校验的回退候选，客户端加载偏好后优先选择仍能产出目标的已保存配方，没有有效偏好才使用该回退候选。

点击后客户端发送目标物品 ID 和当前 JEI 配方 ID。服务端优先从仍打开的 BD 网络菜单取得网络；来自其他界面时使用玩家当前的 BD 主网络。服务端校验成员关系、具体配方、产物和网络可用配方族后打开 Craftlines 订单菜单，客户端不能自行指定任意网络。玩家未设置有效主网络时会收到需要连接网络的提示。

### 4.2 订单界面

界面当前提供：

- 产物搜索与分页列表；
- JEI 入口以具体配方作为不可自动替换的根配方 fallback，玩家显式手动选择可覆盖它；BD 网络按键入口则以保存偏好优先、服务端候选回退的方式选择根配方；
- 可平移、缩放的 EMI 风格递归配方树：目标在上、原料按层向下展开，同一配方层内的相同物品合并并累计数量；
- EMI 风格原料图标网格：成功计划显示本单实际从网络取用的物料，失败计划显示缺料；图标按多行排列、数量叠加显示，悬浮展示精确数量与库存，超出区域时提供滚轮和可见滚动条；
- 悬浮有生产配方的节点时，在物品提示中嵌入所选直接原料 → 单批产物的图形预览，并显示配方族和配方 ID；
- 当前网络中目标物品数量；
- `long` 制作数量输入；
- AE2 风格阻挡模式开关；
- 最近 20 条本人订单的状态、步骤进度和错误信息；默认只展开第一条订单的尚未完成二级步骤，其余订单保持折叠，二级步骤按产物合并并显示“本步已回收/仍需产出”，左键订单标题可折叠或展开；
- 取消本人非终态订单。

已完成和已取消订单均在状态页保留 5 分钟后自动移除；失败订单仍按服务端终态历史条数上限保留。

订单状态同步使用会话级增量协议。首次打开状态页时返回最近 20 条本人外层订单，其中活跃订单携带完整的未完成步骤聚合；后续按客户端配置的刷新间隔只返回轻量订单顺序索引，以及状态发生变化的外层订单头和受影响的步骤聚合。订单进入完成、取消或失败终态时只同步一次终态并清空客户端未完成步骤，终态保持期间不再重复发送详情；5 分钟展示期结束后仅通过索引移除。同步会话丢失或客户端 revision 不连续时自动重新执行一次全量基线同步。
订单状态详情以稳定消息代码和参数持久化，客户端按当前语言渲染；旧存档中的已知英文状态会在读取显示时兼容转换，未知异常只显示本地化通用错误，不向玩家暴露原始异常文本。

菜单创建只保存网络、目标、入口配方以及对共享索引状态的引用，不在开屏路径同步解析完整配方表。JEI runtime 初始化仅收集分类、催化剂和标题元数据，不创建配方 drawable；服务端返回当前主网络可执行的 JEI 类型后，客户端按帧预算在后台把每个已启用 category 完整物化一次，同一 JEI runtime generation 内不重复读取该类型。原生客户端配方查找索引只随真实 RecipeManager 重载失效，新增 JEI 虚拟配方不再让已完成的原生索引整表重建；虚拟配方和规划目录按确定性配方 ID 增量复用。从 JEI 发起订单时会额外确保当前具体 category 已进入预热队列，队列稳定后才打开订单菜单；尚未取得网络类型快照时保守地预热全部 category。全局服务端配方索引从世界 tick 开始后按条数和毫秒双预算渐进建立，任何菜单、快照、提案或下单路径都不得同步补完全表。玩家在服务端索引完成前打开订单页时，客户端自己的树和目录仍照常准备，树区域随后显示服务端索引文字与进度条；服务端索引完成后自动继续库存快照和客户端规划。订单页面的客户端部分仍分为两个初始化阶段：第一阶段增量建立原生产物到候选配方索引；第二阶段保持树稳定显示，同时增量捕获不可变规划目录。只有真实的全量数据包重载、JEI runtime 重建或退出世界才清除对应会话缓存；普通玩家登录同步和单条虚拟配方注册不会清除全局索引。客户端随后经过短暂防抖请求只读库存快照；快照带库存 revision、由服务端索引增量累计的配方 epoch、服务端深度/节点预算并按 256 项分页。后台搜索同时计算库存抵扣和缺料，结果按每页最多 256 个配方选择和 256 个 ingredient 选择上传；服务端此时只组装并短期缓存完整固定选择。点击下单后，服务端只按客户端明确选择的配方 ID 线性复算固定链，不再扫描全量服务端配方。客户端漏传任一实际选择、配方失效或缺少任一材料都会被拒绝，不会回退成服务端分支搜索，也不会创建订单。

服务端索引首次完整建立后由专用守护 I/O 线程原子写入世界目录 `data/beyond_craftlines_recipe_index_v1.json`。再次进入同一存档时先异步读取该文件；格式与当前配方总数匹配即可立即恢复输出到配方 ID 的派生映射和按 family 累计的 epoch，不再等待全量索引。磁盘内容不直接持有或信任配方对象：每次命中目标时仍从当前服务端配方注册表按 ID 取回配方，并重新核对支持性与实际输出；最终下单继续线性复算所选链。因此同配方数量下的旧缓存最多导致某个新目标在本次真实重载前无法命中，不会执行错误配方。服务器运行期间发生真实全量数据包重载时删除磁盘索引并后台重建；普通玩家登录同步不删除。

JEI drawable 物化与规划目录共享每个真实世界渲染帧的 2ms 总预算，且只由世界渲染事件推进一次；JEI 每帧另保留最多 32 条的安全阀。订单树界面打开且玩家正在等待时，目录捕获使用 100ms 时间片，以尽量占用客户端性能但定期归还渲染和输入线程。目录捕获在输出方向、slot 和 candidate 边界检查时间，最终 Catalog 合并也按 holder 分片；第三方 Recipe 自身的输出/输入枚举、匹配和 remainder 调用仍是不可抢占的主线程操作，不能证明线程安全时不会移入后台。原来只提供进度、没有查询消费者的客户端菜单 RecipeIndex 已移除。捕获完成后的分支搜索仍在客户端后台线程执行；候选搜索总墙钟窗口约为 3 秒，偏好方案和 fallback 共用同一窗口。

Forge 1.20.1 的旧式 StackKey NBT 序列化成本显著高于后续版本，因此仅该版本在生成 ingredient 选择键时对默认状态物品使用注册 ID 快速路径：实际栈必须与同物品的新建基线栈 tag 相同且 Forge capability 状态兼容。任一 tag、损伤、药水、附魔、命名或 capability 状态差异都会保留完整序列化身份。1.21.1 与 26.1.2 继续直接使用 Data Components 精确身份，不应用此兼容优化。

客户端收到当前主网络的可执行类型后，会在进入世界的正常渲染阶段预热规划目录。完成目录按有序 holder ID 集合的 SHA-256 指纹持久化到 `config/beyond_craftlines-planning-catalog-v1.dat`，采用流式压缩、原子替换、512 MiB 文件上限以及集合/字符串/NBT 解码上限。缓存读取、GZIP 解压、格式校验和原始 NBT 解析由单线程、有界队列的 I/O worker 完成；worker 到主线程的 encoded-recipe 队列容量为 2，主线程在 output/slot/candidate 边界使用 RegistryAccess 还原 StackKey，因此不会同时深拷贝两份完整目录。退出世界、配方 reload 或 generation 变化会取消旧 load job，旧 generation 不得安装结果；失败或队列饱和回退到主线程增量捕获。完成后的 builder 会立即释放 Level、RecipeHolder 列表和分组组装 map。日志分别记录缓存 header、解压解析、StackKey 解码、配方快照、候选捕获、Catalog 合并、队列深度和主线程最长时间片。resolution-key 身份缓存最多保留 4096 项，候选匹配使用不写缓存的编码路径，退出世界时清空该缓存。

订单数量表示必须新制造的数量，而不是目标库存水位。网络中已有的最终产物只用于右侧“网络已有”显示，服务端规划、材料预留、实际提取和“本单将从网络取用”汇总均明确排除与最终产物等价的资源。

同一产物在一份计划中共享一个配方选择。树中每级输入先按“当前节点尚缺数量 ÷ 单次配方产量”向上取整得到加工次数，再将非复用槽位的单次用量乘以加工次数；容器或稳定工具等复用槽位仍只计一份。树构建期间使用组件感知的库存账本累计扣减，同一批库存不会被多个节点重复判定为可用；库存完全满足的节点为绿色叶节点，部分满足的节点为橙色并显示本单总需求，随后只按剩余缺口继续展开下级原料。同一父配方层内解析成相同物品的重复 ingredient 槽位按完整组件键聚合数量，再创建子节点，因此倍率会逐级向下传播。合并节点保留全部来源槽位，玩家选择候选时会原子应用到整组槽位。启用默认显示折叠时，同一完整资源键（含物品组件）只保留最靠近树根的一次完整节点，后续更深层的重复位置显示紫色跳转引用；没有服务端汇总指标的本地预览会把各重复位置的需求量、取用量和制造量累计到该完整节点。左键引用会将视图定位到浅层完整节点。引用只改变显示，不合并服务端规划步骤或预留。点击包含多个候选的 ingredient/tag 节点会打开 EMI 风格物品网格，网格支持分页和滚轮，当前项高亮；右击产物节点打开统一使用的配方候选页。当前候选存在已保存偏好时，候选页右上角显示“遗忘偏好”按钮，点击后同时删除持久偏好和本次覆盖并恢复自动选择。玩家选择随预览和下单请求发送，服务端按当前配方注册表重新验证，客户端不能提交不产出目标物的配方或不匹配原始 ingredient 的物品。当前展开链路发生循环时仅以红色警告节点截断，不创建跳转引用。

当所选配方把自己的产物资源作为直接输入且单次产出大于该输入的实际消耗量时，该边按自增配方处理，不属于循环或紫色重复引用。加工次数按净增量 `单次产出 - 单次同资源消耗` 计算；同资源下级节点仅显示并预留完成一次配方所需的最小种子数量，其它消耗型输入仍乘加工次数。网络种子不足时，该最小数量继续作为缺料叶节点显示。真实机器、分组机器与供给器无论是否开启阻挡模式都强制逐轮投料并等待本轮产物回收，使产物可以成为下一轮种子；模拟合成可在当前可用种子允许的范围内分批执行。

玩家在候选网格中普通点击配方或 Tag/ingredient 物品后，该选择会立即成为默认偏好，不需要额外按键。配方候选格使用该配方的首个直接材料作为辨识图标，无可解析材料时才回退到产物图标；悬浮展示产物、完整直接原料预览和唯一一行配方类型，格式与机器“已并入网络”提示一致，为“注册表类型 ID（JEI 本地化分类标题）”，无法取得本地化标题时只显示类型 ID。树节点的配方图使用服务端聚合后的实际输入和计划产出数量，候选选择弹窗才显示单次配方原子数量。偏好写入客户端全局文件 `config/beyond_craftlines-planner-preferences.json`，跨单机存档和多人服务器共用；当前实例不存在或不再匹配的配方、槽位和物品会在加载时忽略，服务端仍会在每次预览和下单时重新校验实际选择。

树布局参考 EMI：根节点在画布上方居中，兄弟原料横向排列，深度沿纵向增长。布局只在树内容或 resolution 变化时重建；缩放、平移和悬停期间仍按 Minecraft GUI 的逐帧模型绘制，但会先裁剪视口外的节点和连线，视口外节点不会调用物品栈渲染。

循环警告节点只用于标出再次遇到的祖先资源，不消耗库存，也不继承该资源的全局累计指标。服务端会回滚造成回环的配方分支，把直接发起回环的上级资源按其累计需求记为缺料；该上级节点显示红边，并与右侧缺料汇总保持一致。

固定客户端方案的服务端复算不调用候选分支数或搜索耗时预算，包括原料候选枚举与变体校验；这些预算只约束自动搜索。固定链路仍执行递归深度、循环、配方合法性和库存充足性校验，循环或缺料返回正常缺料结果，不转换成服务端规划上限错误。

客户端方案上传完成后，服务端短期缓存完整固定选择。点击下单时，服务端先按最新库存线性复算整棵固定配方树；缺料时返回错误且不创建订单，可制造时才原子预留网络原料并创建订单。产物目的地默认网络；数量区下方的整行按钮可轮切为物品栏并由客户端记忆。选择物品栏时，全部步骤完成后会检查玩家在线状态和主物品栏容量，再转移本单请求数量，条件不满足时订单保持等待。

### 4.3 阻挡模式

阻挡模式只影响真实机器步骤，不改变工作台模拟合成：

- 开启：每次只发送一次配方所需输入，上一批产物回收完成后才发送下一批；目标机器中仍存在该配方任一输入时暂停发送。
- 关闭：本步骤的剩余批量按机器可接收容量持续投料，不因已有同配方输入而阻挡。

自增配方始终使用逐轮调度；这一安全约束独立于玩家选择的阻挡模式。

每台真实机器同一时间只会被一个活动步骤占用。每个 BD 网络同一 tick 只允许最早创建的一个活动订单取得库存事务权，其余订单保持等待，从而避免跨订单库存事务互相穿插。队首订单会先轮询全部在途机器步骤，再尝试所有依赖已完成的步骤；不同机器可在同一 tick 接受投料并并行加工，同一“维度 + 方块坐标”仍严格互斥。为避免依赖网络产物基线的端点互相误领，同一订单内产出相同完整资源键的外部步骤也视为冲突。运行时每 tick 先用一次线性扫描建立“已认领网络”和“已占用机器”索引，新分派成功后立即加入机器占用索引，并保守地保持到下一 tick，避免同 tick 重复分派。

## 5. 配方发现与递归规划

### 5.1 可见配方

规划器读取服务端 `RecipeManager`，只保留：

- 非 incomplete；
- 至少有一个 ingredient；
- 存在非空物品产出；
- `crafting` 配方，或其配方族在当前网络具有可用执行端点。

可见配方按配方 ID 排序并按 `RecipeManager` 弱引用缓存；数据包同步和客户端配方更新时清空缓存。JEI 下单优先使用展示配方对象或配方持有者自身的稳定 ID，分类提供的展示/书签 ID 仅作后备；服务端分别诊断配方未同步、输入结构不支持、配方族不可用和产物不匹配，避免用同一句错误掩盖不同兼容问题。

### 5.2 配方族

配方树 GUI 的打开动作不等待类型预热或网络可用性预检查；首次类型物化继续在后台按帧推进，页面在类型未就绪时显示加载状态，网络或入口配方错误也在同一页面的报错栏呈现。

实验版的第三方机器关系只来自 JEI 正式 recipe catalyst。客户端以 JEI category UID 作为唯一运行时 family，并从当前 JEI 布局上传有界输入槽、精确资源键、产物与数量；服务端不读取或推断 `RecipeType`，也不加载 alias 或分类白名单。

每个虚拟输入槽同时上传规范化后的 JEI slot name 与消费语义：`CONSUMED` 按制作次数消耗，`REUSABLE` 只要求固定数量，`DURABILITY` 按候选工具剩余耐久和每次损耗折算工具数量。普通 JEI `INPUT` 默认消耗；`CATALYST`（26.1.2 为 `CRAFTING_STATION`）常代表工作站，默认不进入材料协议。只有配方公开 `getTool()` 且候选匹配时才纳入 `tool` 组并推断为每次损耗 1 点耐久；公开 `getOutputContainer()`/`getContainer()` 且候选匹配时才纳入按次消耗的 `container` 组。该推断不按物品是否可损坏、角色名称或展示坐标猜测。

EMI 在 1.20.1 Forge 与 1.21.1 NeoForge 中是可选前端：`RecipeDisplay` Mixin 为可映射回 JEI 的配方预留右侧栏位并加入 Craftlines widget，不依赖生产环境默认关闭的 recipe decorator；hover API 为统一的“下单悬浮资源”按键提供目标。Craftlines 配方树保存或遗忘配方偏好时通过可选桥调用 `BoM.addRecipe/removeRecipe`，`BoM` Mixin 则把 EMI 自身的偏好变更写回 Craftlines 客户端偏好，实现双向同步。所有 EMI 入口与偏好必须重新映射到 JEI recipe ID 并由现有 JEI 布局后端验证，EMI-only 配方不进入执行协议。EMI/JEMI 元数据完成后必须刷新 JEI 输入分组索引，保留供给器和绑定设备的语义子标签。26.1.2 因上游没有对应构件只提供 no-op 桥。EMI 不替换 Craftlines 规划树，也不改变 JEI 为必需执行后端的现状。

JEI runtime 只同步建立分类、催化剂和标题的轻量索引；当前主网络已启用的机器分类随后进入客户端预算队列，每个 category 在本次 runtime 生命周期内完整物化一次，每帧最多处理 32 个 drawable 且不超过 2ms。首次进入尚未预热的具体 JEI 类型时只补该类型，之后所有配方树直接复用；网络入口在缺少类型快照时才保守地预热全部分类。客户端递归规划只读取已经物化并按确定性 ID 缓存的虚拟描述；规划完成后，仅把实际选中的配方按每页最多 8 条上传。服务端校验 category UID 已有网络端点，重新计算描述 ID，并只沿上传的固定链复算。服务端数据包可在 `recipe_io_profiles` 中按 `recipe_type`、`recipe_classes`、`recipe_class_prefixes`、`recipe_id_prefixes` 或 `resource_namespaces` 限定配方结构和动态产物策略。完整的 `dynamic_output` 声明要求 `source=jei_focus`、`identity=exact`、`planning_fallback=same_resource` 与 `execution=assemble_selected_inputs` 同时成立：同资源回退把 JEI 具体产物关联到已验证的服务端配方，并沿该生产步骤或显式资源命名空间传播到运行时产物检测、最终交付和下一步原料选择；实际检测到的栈以自身完整组件键提取、预留和投料，不会被改写成 JEI 模板，缺少任一声明字段时恢复严格匹配。

### 5.3 确定性规划

规划从 BD 网络统一资源库存快照开始。请求数量表示“本次需要制造的数量”，已有目标产物不会抵扣请求。

当一个产物有多个 JEI 候选布局时，玩家已保存的配方和 ingredient 偏好优先于自动建议。未固定部分由客户端建议规划器在同一预算内试规划候选分支，依次按缺失材料总量、步骤数和虚拟配方 ID 选择当前最佳分支。建议上传后，服务端要求每个实际产物都有对应虚拟描述并已固定配方，因此权威复算不再遍历候选分支；缺失描述、ID 不一致或 family 未绑定时拒绝建议。

Ingredient 有多个候选时按以下顺序选择默认值：

1. 网络现有库存数量更多；
2. 可由当前配方图继续制造；
3. 物品 ID 字典序。

自动选择会先试上述基准组合，再逐槽尝试一个备选成员并比较完整子树结果。候选规模是 `1 + 各槽备选数之和`，不会对多个 tag 槽做笛卡尔积；如果最优方案必须同时替换多个槽，玩家仍可在树中手动固定这些 ingredient。

循环只淘汰引入循环的具体配方或 ingredient 组合，不淘汰其兄弟配方及同一 tag 的后续成员。即使优化时间/节点预算已经耗尽，只要尚未找到可制造候选，客户端仍继续检查循环或缺料候选后的下一个成员；找到首个可制造候选后才停止启动新的优化分支。

工作台桶装流体同时保留两种候选：流体代理使用内部 `fluid_proxy/<item>` 选择标识并排在默认候选之前，原始桶物品仍作为正常 item 候选。自动规划在网络有对应流体时优先流体，流体不可用而桶可用/可制造时回退桶；玩家在 ingredient 选择器中显式选择桶会关闭该槽的流体代理，遗忘偏好后恢复流体优先。服务端固定复算、配方树和 `SimulatedCrafting` 都保留同一选择标识，执行时再还原成真实容器物品用于配方模拟。

同一配方中最终选择为相同物品的 ingredient 会先合并，再向下递归。环路、达到深度上限或找不到配方时，相应需求进入缺失材料；存在任何缺失材料时拒绝创建订单。

玩家可按“配方 ID + ingredient 槽位”固定 tag/OR ingredient 的具体物品。服务端要求该物品仍存在于 ingredient 候选集合中。最终选择既写入聚合材料需求，也逐槽写入订单步骤；普通合成执行时只从 BD 网络选择对应物品 ID 且通过原始 `Ingredient.test` 的真实 `ItemStackKey`，避免执行阶段换成另一个 tag 成员。

### 5.4 数量安全

订单数量、计划步骤、BD 存储转移和产量均使用非负 `long`。加法、乘法和向上取整使用饱和运算，超过范围时封顶到 `Long.MAX_VALUE`，不会发生有符号溢出或回绕。

客户端搜索受服务端下发的递归深度和优化节点数约束，并使用客户端固定的约 3 秒候选搜索窗口；预算耗尽只会收敛到当前最佳候选，不会单独拒绝建议。服务端对客户端固定选择只沿已选链路线性复算，不消耗候选节点或自动搜索时间预算；仍保留递归深度、协议分页/选择数、循环检测以及配方和库存权威校验。最终缺料、选择无效、提案不完整或超过递归深度时才会拒绝下单。

服务端生成理论原料统计时同样只沿已经验证的客户端选择展开；任何没有随提案选择生产配方的资源都视为原料叶子，不会因为实际库存满足了该资源而在空库存统计中继续搜索整合包内的其他生产方式。候选材料组合在物化过程中也受服务端规划节点数和时间预算约束，不能在预算检查前生成无界候选列表。

同一配方步骤内资源键相同的重复槽位会先按 `long` 数量合并，再递归规划一次；各槽位原有的配方输入和材料组信息仍分别保留给执行阶段。例如八层 3×3 压缩链只产生八次批量依赖解析，底层数量通过八次乘 9 得到 `43,046,721`，不会按 9 个槽位递归展开为 `9^8` 次服务端计算。

批量合并不会改变可复用输入语义：容器返还后与输入物品及组件完全一致的槽位只按该槽本身的数量计入，不乘合成批次数；同一配方若确实放置了多个可复用槽，则按槽位数合并，而不是按产物数量放大。会损耗耐久或改变组件的有状态工具仍维持逐次执行。

## 6. 工作台模拟合成

`crafting` 步骤不直接把输入替换成静态结果，而是调用服务端原始 `CraftingRecipe`：

1. 按计划固定的 ingredient 物品，从 BD 网络快照为每个槽位选择仍通过 `Ingredient.test` 的真实 `ItemStackKey`；
2. 构造 1×1 至 3×3 的 `CraftingInput`，并调用 `matches`；
3. 调用配方自己的 `assemble` 和 `getRemainingItems`；
4. 校验实际产物仍是计划目标；
5. 模拟检查网络能否容纳产物和返还物；
6. 提取输入并写回动态产物、容器、工具和其他返还物；
7. 任一步骤失败时回滚本次已提取或已插入的内容。

这使定制配方、动态组件、容器返还、耐久工具和不完全消耗物品走同一套原配方语义。

批处理规则：

- 普通可堆叠输入按网络可用量一次结算多次合成，不按每 tick 一个产物执行；
- 输入与返还物的物品和组件完全一致时视为可复用催化剂，整个批次只要求并消耗一份，然后返还一份；
- 返还物是同一物品但组件发生变化时视为有状态工具，本轮只执行一次，让下一轮使用更新后的真实状态；
- 批量返回与消耗都按 `ItemStackKey` 聚合并使用饱和 `long` 运算。

每个成功的模拟合成批次之后，下一普通合成节点至少等待 `virtualCraftingNodeIntervalTicks`。

## 7. 真实机器执行

### 7.1 BD 原生网络炉

原生执行对应：

| 配方族 | BD 机器 |
| --- | --- |
| `smelting` | 网络熔炉 |
| `blasting` | 网络高炉 |
| `smoking` | 网络烟熏炉 |

`0.4.0` 与 `0.5.0` 的完整绑定策略、JEI 分类别名、下单条件、运行时等待状态和三版本
验收矩阵见 [熔炉配方绑定与下单说明](FURNACE_ORDERING.md)。

这三类机器不允许使用网络连接器重复绑定。注册表监听 BD 的绑定/解绑事件以及区块加载、卸载和维度卸载，并按“网络 ID + 配方族”建立索引。

订单从同网络库存提取物品并直接写入炉子的输入存储。产物可能由 BD 自身自动回网，也可能仍在炉子输出存储中，因此订单同时观察网络目标增量和炉子输出；只把本次基线之后出现的产物计入订单，避免误领旧产物。

炉类 JEI UID 在绑定和旧存档加载时统一规范化为执行族：`minecraft:furnace` 与
`minecraft:smelting` 映射到 `smelting`，`minecraft:blasting` 映射到 `blasting`，
`minecraft:smoking` 映射到 `smoking`。有匹配 BD 网络炉时优先走上述原生路径；没有时，
允许回退到配置了同一规范化执行族的供给器。普通绑定机器仍保留原始 JEI UID 语义，
不会因本修复自动变成原生炉替代品。供给器输入组映射键同步规范化，
已有供给器绑定无需清除重建。

### 7.2 直接绑定配方机器

网络连接器允许直接绑定原版及第三方模组的方块实体，但拒绝 `beyonddimensions` 和本模组命名空间下本身已属于 BD 网络的组件。绑定要求：

- 玩家管理当前 BD 网络；
- 目标区块已加载且距离玩家不超过 8 格；
- JEI 将目标方块物品登记为至少一个可映射配方类型的催化剂；
- 目标至少公开一个对应加载器的方块物品处理能力（Forge/NeoForge `IItemHandler`）。

直接绑定不需要供给器。订单通过目标方块无侧面及六个侧面的 BD 已注册资源能力：

- 模拟并选择接收能力最大的 handler；
- 每轮同时选择全部待投原料并完成容量门控；机器内已有与配方资源键完全相同的原料时，该种原料即使占满槽位也视为本轮可投，继续派发其他种类；类型不同且没有可写空间时，本轮不写入任何原料；
- 容量门控通过后，才从 BD 网络提取并投放本轮各类输入；
- 无法插入的余量立即退回网络；
- 记录下单前目标产物基线，只收取基线之后新增且可提取的产物；
- 当前配方声明的全部非目标产物构成抽取白名单；准备阶段会先尝试回收旧副产物，工作期间每 tick 持续抽取白名单资源，不按预计批次产量封顶，只受机器可提取量与网络可接收量限制；
- 网络暂时无空间时保留机器产物并继续等待；
- 机器被拆除、更换、卸载后不可验证或失去物品能力时，订单暂停或进入错误状态。

通用能力无法可靠区分同种物品输入和输出，因此当前拒绝“目标产物同时也是本配方物品输入”的第三方机器步骤。机器配方公开的流体、化学品等输入会通过 BD 已注册的相应方块能力供应；未被配方公开为输入的能量或隐藏工艺条件仍由机器或其他系统自行满足。

### 7.3 合成链供给器

供给器不是直接机器绑定的必需组件，而是独立的订单输入交付模式：

1. 供给器先绑定到 BD 网络；
2. 玩家持网络连接器潜行右击供给器，将其设为临时选择；
3. 再右击 JEI 已登记的原版或第三方机器/催化剂方块，只把识别到的配方类型加入所选供给器的候选集；
4. 普通右击供给器可随时打开 GUI。存在扫描候选时，玩家只能在候选中勾选；候选为空且尚未配置时，界面从 JEI 当前分类中严格单选一个父类型。保存后以该 JEI UID 固化为唯一候选，并可继续配置当前已知的 slot 子标签；
   手动类型没有目标物品图标，客户端沿供给器既有四侧文字兜底链路显示 JEI 本地化配方标题，标题不可用时显示完整 UID；
5. 若配方类型公开了多个逻辑材料组，选中该类型后会在其下显示较窄的材料组多选按钮。材料组按钮按实际数量动态换行，每行最多 4 个；父类型条目随子标签行数增高，本页空间不足时后续父类型自动移到下一页。材料组全不选表示不限制、接受全部组；选中一项或多项后，该供给器只接受所选组；只有一个材料组时不显示二级按钮并自动接受；
6. 对应已启用配方族执行时，订单按材料组把同一步骤输入原子分发到相应供给器，并等待产物完整返回网络。候选端点先按材料组匹配精度排序：显式选择当前组的端点优先，未选择任何组的通配端点作为剩余组的兜底；同一精度内再按维度和坐标稳定排序。一个步骤使用多个供给器时会同时占用所有参与端点，避免并发订单串料。

供给器拒绝玩家和管道写入，只有订单事务能短暂打开写入门。外部能力可以提取。GUI 右下角的“全部送回网络”按钮默认不可用，在供给器存在资源时通过菜单数据同步启用；点击后由服务端把网络能够接收的全部资源送回当前 BD 网络，网络容量不足时将未接收余量原样留在供给器中。

已启用至少一种配方类型后，连接器普通右击供给器进入无线设备连接模式；供给器自身不选择面，随后右击目标设备的面记录 `(维度, 坐标, 面, 方块 ID)`。同一设备再次点击另一面会原位更新，点击当前面则断开。每个供给器默认最多 16 个目标，由服务端 `provisioner.maxWirelessConnections` 在 1–1024 范围内配置。GUI 的“已连接设备”行右侧使用一个 120×18 按钮循环选择轮询、最近优先和最远优先；策略保存在供给器 NBT，旧存档默认为轮询。服务端 `provisioner.resetRoundRobinOnRecipeActivation` 默认开启：每次独立配方请求成功激活参与供给器后，轮询游标在下一次投料前重置到第一条绑定；阻挡模式每完成一批并激活下一轮时再次重置。关闭后游标继续跨请求轮询。同维目标按供给器与目标坐标的距离平方排序，跨维目标按无限远处理。暂存资源只通过所选面的 BD 已注册能力直接投送；任一目标失效、容量为零或实际拒收当前资源时，保留余量并继续尝试本策略中的下一个目标，不会卡死在首选目标。连接器在手时会高亮所选供给器、已连接面和准星下候选面。供给器 GUI 倒数第三行与 Jade 显示当前连接数。清空全部已启用类型时连接列表同时清空；手持连接器左击供给器打开配置 GUI。潜行右击供给器仍保留为配方候选扫描入口。

网络连接器在配方候选扫描模式下对空气使用会清空当前所选供给器的候选、已启用配方类型和无线设备连接；在无线设备连接模式下对空气使用只退出本次连接选择。候选、最近一次成功扫描的目标方块 ID 及其“选取方块”物品堆栈保存在供给器方块实体；物品堆栈同步为实例级模型数据，其 GUI 物品模型被压平、缩放为 8×8，并以保留原贴图完整 alpha 的透明渲染层合入供给器四个水平侧面的纯色 8×8 底板。若物品使用 GeckoLib、ISTER 等自定义渲染器，或其烘焙模型没有可用四边形，则不尝试逐帧渲染该复杂物品，改由轻量方块实体渲染器在四侧提交等比缩放的本地化设备名称；失败判定与名称布局按物品和文案缓存，且 32 格外不提交。顶部仍保留供给器自身图案。客户端收到目标变化后会刷新模型数据并立即重建对应区块网格，无需等待下一次方块更新。已启用类型及按配方族保存的材料组白名单保存在绑定 SavedData；旧存档和空白名单均迁移为“接受全部”。服务端保存配置时会再次验证已选类型是候选子集、材料组是该类型公开组的子集。供给器模式与机器直接并网是两条独立路径。

## 8. 绑定持久化与视觉

绑定记录保存在主世界 SavedData `beyond_craftlines_bindings`，包含所有者、网络 ID、维度、坐标、设备类型、JEI 类型、配方族和绑定时方块 ID。运行时按玩家、网络、位置和供给器端点建立索引。

普通绑定：

- 网络连接器右击原版或第三方机器：绑定；
- 潜行右击已绑定机器：解绑；
- 手持连接器左击已绑定机器：勾选配方类型及该机器负责的材料组；空材料组选择表示通配；
- 供给器与已绑定机器配置 GUI 的倒数第二行都提供 `-10`、`-1`、当前值、`+1`、`+10` 优先级控件；数值持久化到绑定记录，旧存档默认为 `0`；
- 同一步骤的不同材料组可同时分配给多台直接绑定机器和供给器。显式材料组优先于通配端点；同一材料组匹配等级内数值较高的配置优先级先被选择，再由直接机器优先和坐标稳定排序；同组且同配置优先级的多台直接机器会一起预留以容纳单槽基座等分布式输入；
- 只有目标网络管理员可以解绑；
- 方块被破坏时移除关联记录；
- 加载后会校验维度、方块 ID、网络和能力，防止坐标处更换方块后沿用旧绑定。

直接绑定的机器会显示 BD 风格的黑蓝青三层线框。实现使用 `RenderType.lines()` 在方块实际碰撞/轮廓包围盒外分层绘制，不替换方块材质，因此不会与原材质争夺同一深度面而产生材质闪烁。

客户端登录、切换维度和绑定变化时接收服务端快照。快照按区块索引，渲染只遍历玩家附近区块，并再次校验距离、区块加载状态和方块 ID。

## 9. 订单状态与持久化

订单状态：`QUEUED`、`RUNNING`、`PAUSED`、`COMPLETE`、`CANCELLED`、`ERROR`。

`RecipeOrderJob` 保存：

- 订单 UUID、所有者和网络 ID；
- 目标、请求数量和阻挡模式；
- 已解析步骤、每个步骤的前置依赖及独立完成状态；
- 每个步骤各自的下次普通合成允许时间；
- 每个在途步骤各自的外部机器等待上下文，包括机器位置、产物基线、目标数量、已收取数量和剩余输入。

订单保存在主世界 SavedData `beyond_craftlines_recipe_orders`。重启后可同时恢复多个在途机器步骤并继续推进；旧版单游标订单会按原顺序迁移为保守的串行依赖链。没有状态变化时不会重复标脏存档；终态历史按配置只保留最新若干条。

取消只允许订单所有者操作，并且不会撤回已经送入机器、供给器或已经完成的步骤。

## 10. 网络协议与安全边界

当前协议包括：打开菜单、请求分页规划快照、分页上传客户端固定选择、提交目的地并触发服务端权威复算、取消订单、请求订单状态、请求网络物品数量、绑定/解绑机器以及同步绑定视觉。

所有改变状态的请求都在服务端重新校验菜单类型、玩家身份、网络上下文、距离、手持物品、目标资源 ID 和权限。客户端提供的 JEI category 只是候选，必须与服务端已加载配方类型再次匹配。

以下协议上限固定，不开放配置：

- 字符串最大 256 UTF-8 字符；
- 单次绑定最多 32 个 JEI 配方类型；
- 绑定目标必须在玩家 8 格内；
- 订单数量必须为正 `long`，非法或非正输入归一为 1。
- 规划库存快照和建议上传每页最多 256 项、最多 64 页；必须按 nonce 和连续页码组装。
- 已完整上传的客户端固定选择最多缓存 30 秒，未完成的建议上传最多保留 10 秒。

这些上限用于保证解码和权限边界，不属于玩法调节项。

## 12. 性能设计

当前实现采用以下约束避免随配方、订单或绑定数量失控：

- 配方规划具有深度、节点和时间三重预算；
- 数量计算使用饱和 `long`，不因复杂树溢出；
- 同配方重复 ingredient 在递归前聚合；
- 可见配方和产物索引缓存，并在配方重载时失效；
- 普通稳定合成按长整型批次执行，不按十亿次循环；
- 只有有状态返还工具逐次模拟；
- 订单调度只扫描受配置限制的活动订单，终态历史有界；
- 订单步骤以依赖完成状态构成就绪集合，同订单内互不依赖且机器不冲突的步骤可并行等待真实加工；
- BD 原生网络炉按网络与配方族索引；
- 绑定与供给器记录按常用查询维度索引；
- 客户端绑定边框按区块索引并受距离限制；
- 无状态变化的等待 tick 不重复写脏 SavedData。

## 13. 当前兼容边界

本模组承诺的是基于 BD `IStackKey` 与已注册能力的通用配方和机器编排，不承诺理解每个模组的内部工艺状态。

- 工作台类定制配方：由原配方 `matches/assemble/getRemainingItems` 决定，支持动态结果和返还物。
- 原版及第三方机器：要求 JEI catalyst、可上传的 JEI 布局和可用 `IItemHandler`；不要求服务端 RecipeType 映射。
- 供给器扫描工作站时不要求目标拥有方块实体或物品能力。原版酿造台、锻造台、堆肥桶、铁砧和切石机只允许绑定供给器，不开放直接机器绑定。其他具有可自动化物品能力的机器既可以走供给器，也可以直接绑定 JEI UID。服务端重新计算包含 slot 子标签的确定性虚拟配方 ID，并要求当前网络存在同 UID 的有效端点。
- 配方中的 `energy`、`power`、`FE` 等数值元数据不视为 ingredient，也不推断单位或换算关系；机器能量与其他专用工艺条件由真实机器自行处理。公开为 ingredient representations 且能转换为 BD 已注册资源键的物品、流体、化学品等真实输入会正常规划与供应。
- 配方和 ingredient 选择当前按输出物品、配方槽位作用于整棵订单树；相同输出或相同配方槽位的重复节点共享选择。
- Ingredient 自动选择、客户端偏好、上传协议、服务端固定复算和订单持久化统一保存完整资源身份令牌；1.20.1 使用 NBT、1.21.1/26.1.2 使用 Data Components 序列化摘要。同一物品 ID 下的不同药水或有状态物品不会互相匹配；旧版仅含物品 ID 的偏好仍作为兼容回退。
- 右侧缺料/提取汇总在规划完成前保持计算中，不再从当前界面选择另行构建理论树；完成后，树节点选择、服务端节点指标和右侧材料表共同投影同一份已验证计划。规划结果明确区分 `READY`、`NO_RECIPE`、`MISSING_INPUTS`、`CYCLE`、`BUDGET_EXHAUSTED`、`RUNTIME_UNAVAILABLE` 与 `STALE`。
- 打开配方树的服务端门禁失败时，不允许只向聊天栏或日志报告。网络不可用、JEI 类型无执行端点、虚拟描述非法、配方不可用等错误必须随新菜单同步到页面；页面进入终止错误态后立即取消目标配方搜索和后台规划、清空所有 loading 文案并禁用下单，后续 tick 不得重新显示“正在搜索”。
- 真实机器无法证明某个新产物一定由本订单产生，只能通过下单前基线与数量增量隔离；机器应避免被其他自动化同时操作。
- 机器或相关区块必须已加载，模组不会主动加载区块。
- 供给器交付后步骤即视为完成，它不等待或回收外部加工结果。
